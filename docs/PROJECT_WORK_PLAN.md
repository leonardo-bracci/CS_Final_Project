# Final Project Work Plan

Use this file as a running checklist for the next 8 weeks. The goal is to finish with a polished, well-documented project that clearly meets the rubric and leaves room for a high grade.

## Goal

- Build a working final project with at least 3 pre-trained models in different data spaces.
- Show clear model testing, comparison, and decision-making.
- Deliver a clean prototype, a strong report, and evidence of iteration.

## High-Score Strategy

- Keep every stage tied to the rubric.
- Prefer a smaller system that works reliably over a larger system that is only half-finished.
- Save evidence as you go: notes, screenshots, test results, rejected model choices, and performance observations.
- Make the final write-up explain why each model was chosen and how the pipeline works end to end.

## Stage 1: Lock the Scope and Requirements

### Week 1

- [ ] Re-read the assignment brief and extract the grading criteria into a short notes section.
- [ ] Confirm the project problem statement in one sentence.
- [ ] Define the three model domains you will use.
- [ ] List the exact input and output for each stage of the pipeline.
- [ ] Decide what counts as a successful prototype.
- [ ] Create a folder for notes, test evidence, and screenshots if needed.

### Week 2

- [ ] Write a short architecture sketch for the full pipeline.
- [ ] Decide which parts are already working and which parts still need implementation.
- [ ] Identify any model or library risks early.
- [ ] Write the first version of the project README summary.
- [ ] Create a log of candidate models and why they may or may not fit.

## Stage 2: Build the Core Prototype

### Week 3

- [ ] Finish the first model stage so it works consistently.
- [ ] Make sure the stage returns structured data that the next stage can use.
- [ ] Add a minimal test for the main logic.
- [ ] Save one example run and note any problems.

### Week 4

- [ ] Implement the second model stage.
- [ ] Connect stage 1 output to stage 2 input.
- [ ] Verify that the pipeline can run without manual intervention.
- [ ] Add error handling for missing input, failed model loads, or bad outputs.
- [ ] Write down any tradeoffs or model issues you found.

## Stage 3: Complete the Three-Model Pipeline

### Week 5

- [ ] Implement the third model stage.
- [ ] Connect all stages into one coherent workflow.
- [ ] Confirm that the final output is understandable and useful.
- [ ] Check that each stage uses a different data space where possible.
- [ ] Record the exact model names and versions used.

### Week 6

- [ ] Run the full pipeline several times.
- [ ] Test the system with realistic and edge-case inputs.
- [ ] Measure runtime or responsiveness if relevant.
- [ ] Compare at least one alternative model or approach if feasible.
- [ ] Keep short notes on what worked best and what was rejected.

## Stage 4: Improve Quality and Evidence

### Week 7

- [ ] Clean up the code structure and remove prototype-only clutter.
- [ ] Improve function names, docstrings, and comments where helpful.
- [ ] Expand tests for the most important logic.
- [ ] Capture screenshots or output samples from the working system.
- [ ] Update the README with installation, usage, and project overview.

### Week 8

- [ ] Write the report or final write-up outline.
- [ ] Add a section explaining model selection and rejection.
- [ ] Add a section explaining architecture and workflow.
- [ ] Add a section describing testing and limitations.
- [ ] Proofread everything for clarity and consistency.
- [ ] Do one final full run of the project and save the result.

## Deliverables Checklist

- [ ] One clear project description.
- [ ] Three model stages integrated into one pipeline.
- [ ] Evidence of model testing and comparison.
- [ ] A working prototype.
- [ ] Tests for core logic.
- [ ] README with setup and usage instructions.
- [ ] Final report or write-up with decisions and evaluation.

## Evidence To Save As You Go

- [ ] Notes on model candidates.
- [ ] Notes on rejected models and why they were rejected.
- [ ] Short test outputs or terminal logs.
- [ ] Screenshots of successful runs.
- [ ] Bug list and how each bug was fixed.
- [ ] Any simple performance observations.

## Final Quality Bar

- [ ] The project runs from a clean setup.
- [ ] The pipeline is understandable without you explaining it live.
- [ ] The report explains the purpose, method, and decisions clearly.
- [ ] The system feels complete rather than just partially scaffolded.

## Weekly Review Questions

- What did I complete this week?
- What is still missing?
- What is the biggest risk right now?
- What evidence should I save before moving on?
- What will make the project easier to defend in the final submission?
